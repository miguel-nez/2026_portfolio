Design system · documentation · sole UX designer

Solid Design System /
documentation, patterns, landing page

The design system of Union Investment, a large German asset manager. When I joined, most components were built but not yet documented for the people designing with them. My work was to define how the system is documented, to research UX patterns shared across the company's products, and to present the system to the teams who had not adopted it yet.

My role

Experience designer, sole UX designer on the project

Ownership

Documentation structure and language · user research · pattern library · landing page structure and design

Team

One colleague on the pattern library · one visual designer on the landing page · the client's design system team

Recognition

UX Design Awards 2024 nominee

The problem

The Solid Design System is a framework-agnostic component library for Union Investment's digital products. It is built on design tokens, so colours, typography and spacing are defined once and shared between Figma and code, and components have the same names and properties on both sides. When I joined, most components were already well into development. They were built from the many versions of the same elements that existed across Union Investment's products.

The documentation was written for developers: properties, values and technical specs. What was missing was the layer for the people designing with the system. When should a component be used, and when not? What is the difference between two similar components? What does accessibility require from the person using it? Without these answers, teams kept building their own solutions, and the same form or search existed in slightly different versions across products.

Approach

01

Understanding the system and its history. It was my first design system of this size, so I started with research. I went through the existing components and compared how other public design systems document theirs. I also audited how the older versions of each component were used in Union Investment's products. This showed me which differences were accidental and which came from real needs that the new system did not cover yet.

02

Asking designers and developers. I ran surveys with both groups about how they used the documentation and where it failed them. I asked about concrete situations where they had lost time, not about what documentation should contain in general, and used the answers to iterate on the structure.

03

A structure and a language for every component. From the research I defined a fixed structure for each component page, so designers and developers find the same information in the same place.

Example and links

A live default example, with links to the Storybook documentation, the Figma library and the Figma component docs, and to related components and templates.

Common use cases

Concrete situations where the component is the right choice, for example a single FAQ item or optional sections in a long form.

Usage guidelines

Rules for each slot and for the content, and comparisons where two components overlap, for example when to use an accordion instead of an expandable.

Accessibility information

What the designer has to take care of when using the component, linked to the system's best practices for WCAG compliance.

The language is defined as well. Guidelines are short instructions that start with a verb, like use, keep, ensure or avoid, and component, slot and property names are the same in Figma and in code. This keeps the documentation consistent when other people add new components, which was the main goal, because the system had to keep growing after my part of the project ended.

↑ Component documentation page in Storybook, the structure I defined

04

Finding middle ground with the client. The second phase was a pattern library: recurring combinations of components, such as a form or a search, documented for teams across the company. The client wanted ready-made blocks that teams could copy into their products and use right away. That is a fair goal, because speed helps a lot with adoption. My concern was that one fixed layout would not fit all the different products, and that teams with other needs would end up changing the blocks in their own way. After a few sessions together we agreed to do both.

Patterns

For each pattern, its anatomy, its logic and best practices, so teams can build their own version and still stay consistent.

Ready-made blocks

Copy-paste blocks for the most common forms: login, password reset, contact and personal information.

The patterns give teams the rules, and the blocks give them a fast start for the cases that look almost the same in every product.

05

Finding the patterns. I led this work, with support from a colleague. We made an inventory of the products to find where different teams had built the same solution independently. Interviews with stakeholders helped us set priorities and find patterns that were obvious from the inside but not from the outside. We started with forms, search, navigation, first-time use and data visualisation.

↑ Pattern definition, Forms

Forms is a good example of what a pattern contains. It starts with a definition and a few principles, like asking only for the information that is really needed. Then comes the anatomy of a form, ten elements from the description text to the action buttons, and the related components for each type of input. The best practices cover how to help people while they fill in a form, how to split a long form into steps, and when to validate: on submit by default, and on blur only for format errors that are easy to fix, once the value has changed. A separate page gives rules for error messages. They explain how to fix the problem and don't blame the user, so "Please enter your first name." instead of "Fill this field." At the end are the four ready-made forms, each for desktop and mobile.

06

The landing page. The system also needed a public page to present it to the teams who had not adopted it yet. I defined the structure and the content of the page and designed it, and a visual designer took care of the final visual details. The page is built with the system's own components, so it shows the system working while it explains it.

06

Release notes

A link to the latest changes, so the page stays current

The sustainability section was a conscious choice. A design system is usually presented with speed and efficiency, which is a weak argument for a team that is already busy. Reusing components instead of building them again also means less code, less data transfer and less energy. The page shows estimates such as 50% faster development and 20% lower CO₂ emissions, and states that its own carbon footprint is about 95% lower than an average page of similar complexity.
